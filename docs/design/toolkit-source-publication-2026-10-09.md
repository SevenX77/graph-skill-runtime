## Decision and alternatives

The selected path preserves the four installer archives and commits their verified source inputs on an isolated branch. The coordinator compares packaged files with that source using the six explicit line-ending exceptions above, compares runtime wheel bytes exactly, then rebuilds the generated JavaScript and HTML from the committed inputs and compares those outputs exactly with the shipped files. A passing comparison establishes correspondence for the tested content; native operation retains its separate acceptance criteria.

The coordinator then publishes the branch and opens a pull request. After rechecking the release identity and old tag value, the coordinator changes the mutable tag to the verified source commit using an expected-old-reference precondition. That condition prevents an intervening tag change from being overwritten. The release receives the supplemental provenance asset and notes identifying the recovered source. GitHub's automatic source archives must be downloaded and inspected for the toolkit contents and their relationship to the recorded commit.

This approach has feasibility `0.95`, based on the reported mutable release, write access, available original inputs and preserved artifacts. The remaining uncertainty is source correspondence under the declared normalization and exact generated-output correspondence. A difference beyond that normalization stops tag repair and requires review of the source selection or a replacement build. Changed release permissions or a changed tag likewise stop the dependent remote action.

A new `0.2.1` build is a viable alternative in principle; its feasibility is **unassessed** because a new complete candidate has not been built or inspected. It changes the downloadable bytes and requires a fresh artifact identity and acceptance cycle. When the existing bytes can be associated with complete committed source, that extra candidate supplies no necessary functional change. It becomes relevant if correspondence cannot be established. Retaining the artifact-only publication is rejected because it leaves the user's explicit source requirement unmet.

The publication review also identified the existing Python release workflow's failed exact-version guard for this toolkit tag. The coordinator implemented a narrowly scoped job condition selecting tags that start with `v`, preserving the existing exact `v<pyproject version>` check and keeping toolkit publication outside the Python release path. The [workflow](../../.github/workflows/release.yml) owns the executable condition. Its remote behavior requires its own evidence.
