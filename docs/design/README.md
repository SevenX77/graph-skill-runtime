# Standalone Design Documentation

This directory routes current Graph Skill Runtime facts, historical evidence, and the still-drafted complete v1 target. The current checkout targets distribution `1.0.0a1`, retains portable syntax `gskill.graph.v1`, and implements the provider-neutral Agent kit defined in [`unified-agent-kit.md`](./unified-agent-kit.md). Phase 1 implemented the standalone identity and typed runtime boundary. Phase 2 implemented the portable file format, flat graph registry, and explicit legacy converter. Phase 3 implements durable cooperative host-native handoff for explicitly serializable Agent wait points in a root DAG. Phase 4 implements capability-probed direct vendor CLI execution over that same bounded wait-point contract. Phase 5 is accepted for its separate canonical MoirAI bundle, six host renderers, read-only discovery, and explicit safe installer. Historical Phase 6 evidence accepts one `0.1.0a1` candidate for same-candidate artifact binding and installed-package behavior on Ubuntu, Windows, and macOS; the current uncommitted `1.0.0a1` bytes have local Windows package smoke only. Phase 3b host-native expansion, first-release naming review, and actual release/registry publication remain unfinished, so the complete v1 target remains drafted.

## Current Phase 1 through Phase 4 line

The standalone naming cutover is complete in source and package metadata. Public callers use the typed `graph_skill_runtime` facade, not the extracted engine's former top-level ABI. The installed-interpreter module CLI and `gskill` MCP server are transport adapters over the same `RuntimeApplication`, and `create_application` composes replaceable engine and snapshot ports without a singleton.

The current reader accepts only the portable contract in [`01-PORTABLE-GSKILL-V1.md`](../skill-spec/01-PORTABLE-GSKILL-V1.md). A business gSkill is always supplied by path and remains user-owned; installing or importing the runtime does not register, discover globally, copy, or mutate it. The root `SKILL.md` is the sole Agent Skills discovery target and requires `metadata.gskill: gskill.graph.v1`; `graph.yaml` owns machine topology and requires `schema_version: gskill.graph.v1`. Distribution and syntax majors must match, and a missing or mismatched root marker fails with `[F-v3-skill-metadata-invalid]`. Reusable graphs live in one flat `graphs/<graph_id>/` registry.

Legacy v0.3 parsing is isolated behind `python -m graph_skill_runtime migrate studio-skill SOURCE DESTINATION [--runtime-config PATH] [--preset-id ID]`. The converter does not modify source or overwrite an existing destination. Production compile, predict, run, inspect, SDK, module CLI, and MCP paths neither sniff formats nor fall back after a portable-format failure.

The default executor is `host-native`. A root graph without an Agent phase runs directly. For a supported root-DAG Agent wait point, the runtime first persists a LangGraph SQLite checkpoint, then persists a provider-neutral `AgentTask` in a separate handoff database, and only then returns `RunResult(status="agent_required")`. The host creates exactly one fresh clean-context native child and submits the typed result through the Python SDK, MCP, or `python -m graph_skill_runtime submit`; the runtime validates and applies that result to the same graph run. `resume(checkpoint_ref)` observes or reopens the durable wait or terminal response and never submits Agent output.

The current Phase 3 address is deliberately narrow: Agent phases in registry subgraphs, graph-level or phase-level iterate, and incomparable parallel branches fail fast. Host-native Agent handoff requires SQLite checkpoint storage. Ordinary human/breakpoint resume and host-native lifecycle acknowledgment remain Phase 3b work. Explicit `embedded` execution still reaches the extracted engine.

Explicit `cli` execution now uses the same durable Agent task/result transition through one fresh vendor process per task. Claude, Codex, GitHub Copilot, Cursor, Gemini, and OpenCode protocol adapters probe their executable, version, required flags, and any exposed authentication state before handoff creation. Pure `LOGIC` graphs do not construct or probe a vendor executor. The path rejects unbridged portable tools, subagents, subgraphs, and framework context access; it never silently chooses `embedded`. `agent_dispatched` records a built immutable CLI attempt, `agent_started` records the owned process-tree root, and a successful `agent_completed` shares their `attempt_id`. A post-dispatch execution failure emits non-terminal `agent_failed` evidence and leaves the durable task retryable.

POSIX process groups remain the primary process-tree owner. Hosted Darwin established that group-wide `killpg` can return `EPERM`; the current narrow fallback enumerates bounded `ps` output and individually signals only exact-PGID members owned by the runtime effective UID. It does not broaden cleanup into a guessed descendant tree.

All six adapters have fake-process contract coverage, but only Codex CLI `0.144.1` on Windows `10.0.26200` x64 with Python `3.11.15` has a successful real operational smoke. Claude Code `2.1.222` passed executable/version/help probes there but lacked authentication; the other four CLIs were absent. On the same Phase 4 commit, [GitHub Actions run 33140732333](https://github.com/SevenX77/graph-skill-runtime/actions/runs/33140732333) passed quality gates, Python 3.11/3.12/3.13 runtime tests, and Windows/macOS cross-platform smoke; CodeQL and Analyze Python passed as well. This is source-checkout platform evidence, not real macOS/Linux vendor execution. Phase 6 later established a separate installed-package evidence chain without running a real vendor CLI.

## Current provider-neutral Agent kit

The packaged Agent kit is an operating layer for arbitrary coding Agents, not a user business gSkill and not a host plugin. `python -m graph_skill_runtime guide agent-configuration` returns the canonical AGENTS section, ten standalone indexed rules, exactly two complete Skill/reference trees, and placement choices as read-only JSON. It performs no writes and there is no unified-kit setup/install command. The owner chooses host, user/project scope, rules-tree destination, Skill destinations, and manual versus explicitly authorized Agent editing. Every write requires inspection, an exact additive plan, and approval; existing instruction files are preserved.

The `gskill` Skill operates an existing root marked `metadata.gskill: gskill.graph.v1`; `create-gskill` owns natural-language create/scaffold/convert/brainstorm/design/structural-redesign requests and does not apply to ordinary Agent Skills. Runtime calls remain MCP-first with `python -m graph_skill_runtime` as the unavailable-MCP fallback. Each `agent_required` wait requires exactly one fresh native clean-context child using the canonical prompt owned only by rule 05. Users do not select internal specialist roles. The [unified design](./unified-agent-kit.md) owns the complete assets, routing, handoff, configuration, and acceptance criteria; the MoirAI integration below remains separate.

## Accepted Phase 5 integration scope

The source checkout contains one manifest-closed MoirAI bundle at asset version `1.0.0`: provider-neutral bodies for `moirai`, `moirai-clotho`, `moirai-lachesis`, and `moirai-atropos`; eight Agent Skills; and `KB-00` through `KB-14`. The bundle contains no `graph.yaml` and does not register a user business gSkill. `PackagedMoiraiAssets` reads and validates that inventory; six renderers project it into the selected host's native skill and agent directories and register the existing `gskill` MCP server. Canonical specialist names remain hyphenated. The Codex renderer alone normalizes its safe identifiers to underscores, for example `.codex/agents/moirai_clotho.toml` with `name = "moirai_clotho"`; other hosts retain the manifest's hyphenated names.

`IntegrationInstaller` construction and PATH detection are read-only. Only an explicit install call authorizes writes. Install and uninstall preflight all requested targets, refuse unmanaged or modified resources, merge only owned shared-config selectors or a marker-delimited Codex TOML block, maintain per-target manifests, and remove only exact unmodified owned hashes. After an apply failure, rollback restores a touched path only if its bytes still equal that operation's after-image. A concurrently changed path is preserved and causes an incomplete-rollback error. `.opencode/opencode.json` is shared configuration: the installer owns only `mcp.servers.gskill`, plus manifest-owned projected files, and fails closed when sibling `opencode.jsonc` exists. The CLI and five integration SDK functions expose detection, planning, installation, and uninstall; the MCP server remains exactly eight runtime tools and has no installer tool.

Phase 5 acceptance separates three kinds of evidence:

- **Source candidate:** Ruff passed; strict mypy passed over 149 source files; the contract manifest validator passed; and the complete pytest result was `1715 passed, 1 skipped in 83.51s`. [`moirai_renderers.json`](../../tests/integrations/snapshots/moirai_renderers.json) fixes Claude, Codex, Copilot, Cursor, Gemini, and OpenCode output for both project and user scope, including native paths, profile metadata, and MCP shape. This snapshot proves deterministic rendering, not six operational host products.
- **Built artifact:** `uv build` produced the `0.1.0a1` sdist and wheel. The wheel contained exactly 28 MoirAI members: one `integration.json`, four role bodies, eight skills, and fifteen knowledge files, with no `graph.yaml` or extra member. A clean Python 3.11 environment installed that wheel, read the `4/8/15` inventory through `PackagedMoiraiAssets`, and used the installed wheel's `gskill` to project a temporary project. The wheel smoke passed. `pip-audit` reported no known vulnerabilities among resolved distributions but skipped the unpublished local project; it is neither a source-security audit nor publication evidence.
- **Real host:** On Windows `10.0.26200` x64, Claude Code `2.1.222` discovered eight project skills and all four projected agents, found the project `.mcp.json` entry, and started and connected the `gskill` stdio MCP server. A valid `moirai-clotho` selection passed profile discovery and stopped only because the host was not authenticated. This proves skill, agent, and MCP discovery plus server startup, not authenticated model execution. Codex CLI `0.144.1` independently supplied the project `$moirai` skill and successfully called project MCP tool `gskill.inspect` for `hello-world`. Its observed spawn surface had no `agent_type`; the child recorded `agent_role=null` and did not receive the custom `developer_instructions`. Codex custom-agent invocation is therefore unverified, without contradicting the official standalone TOML format.

These source, artifact, and bounded host observations satisfy the Phase 5 exit criteria. They do not claim that all six products are operational and do not add Studio or Gateway plugins.

Phase 6 binds one wheel/source-distribution pair to an exact source commit, verifies that pair before installation, and records installed-package evidence for pip-wheel, uv-wheel, and pip-sdist on Ubuntu, Windows, and macOS. The smoke imports from the isolated installation; proves the absence of console entries and package-owned launchers; invokes that environment's Python with `python -m graph_skill_runtime`; verifies module-CLI behavior, the read-only guide's zero-write repeatability, and exactly eight stdio MCP tools; and exercises durable host-native reopen/submit, SQLite reopen and file-handle cleanup, non-ASCII and space-containing paths, and the MoirAI project lifecycle without unexpected host configuration writes. ## Drafted Phase 3b line

Phase 3b expands host-native wait-point addressing, standalone human/breakpoint typed resume, and host acknowledgment or capability negotiation. It remains authoritative design direction in `v1-alignment.md`, but it is not a current capability. First-release naming and publication conditions are separately owned by the next section. Gateway and Studio plugins are outside this release line; the design retains only the ownership rule that any future integration uses public external Port/Adapter boundaries and does not move product-specific truth into runtime core.

## Publication and cutover rules

The GitHub repository exists and uses pull-request-only protection. The distribution name is present in local package metadata, but the project has not been published to PyPI or TestPyPI. [The release workflow](../../.github/workflows/release.yml) checks a GitHub Release tag against the package version, builds and manifests one candidate, requires source and installed-package acceptance on all three operating systems, and allows only the original verified distributions to reach PyPI Trusted Publishing through OIDC. No tag release or GitHub Release has been created, and the owner still has to create the PyPI project and configure and verify its trusted publisher. An accepted release candidate is not registry or release evidence.

Each future contract cutover replaces its predecessor only after implementation, regeneration or conversion, cross-platform verification, contract-map updates, examples, and documentation are complete together. The Phase 2 source cutover follows this atomic shape: one production reader plus one explicit converter boundary, with the old format retained only as `superseded` evidence. Do not add a dual reader, legacy alias, deprecated field, or version-guessing fallback. Historical evidence stays historical; current facts move to the current owner.
