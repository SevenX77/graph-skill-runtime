# Graph Skill toolkit architecture

<a id="shared-view-and-host-delivery"></a>

The toolkit is a local application for Graph presentation and host operations, with an explicit installer. Its backend runs on the same physical filesystem as the selected business gSkill, and one shared HTML frontend displays the graph in Codex or Claude. A gSkill is a user-owned directory containing `SKILL.md`, `graph.yaml` and phase definitions. After the application selects that directory, backend file observation and the frontend's own data connection keep its displayed graph current after saves. The [Host Port](ADAPTER.md), a contract for requesting native host operations, separately governs identity, capabilities and button actions.

The source sits at `src/graph_skill_toolkit/` beside `src/graph_skill_runtime/`, the separately packaged Python runtime. The runtime owns compilation and execution, and it is the single authority for gSkill validity and its messages. A compile diagnostic is one structured finding from the runtime command `compile --no-cache <root>`, carrying a code, severity, message, source path, line and field path. The toolkit draws only graphs the runtime accepts: its graph reader projects the root topology and phase kinds of an accepted graph for display. For a graph the runtime rejects, the toolkit shows the runtime's compile diagnostics verbatim. [The decision record](../../docs/design/canvas-runtime-diagnostics-2026-10-14.md) records this ownership.

The browser [entry](app/main.tsx) constructs a `GraphConnection` through [the graph client](application/graph/client/index.mjs) and a host adapter through [the adapter factory](adapters/factory/index.mjs). `GraphConnection` defines startup callbacks, selected-root changes and disposal for graph data. The [workbench](ui/workbench/index.tsx) composes those independent connections. It renders the graph from `ui/canvas/`, the invalid-graph notice from [`ui/diagnostics/`](ui/diagnostics/index.tsx) above the graph area when the runtime rejects the selected skill, live host identity from `ui/host_status/`, and the 15 operation choices from `ui/interface_lab/`. The interface lab uses `application/graph/interface_samples/` to prefill optional JSON arguments when a business root exists. Each operation directory under [`host_interfaces/`](host_interfaces/) contains `index.mjs` for the shared definition, `codex.mjs` for the Codex mapping and `claude.mjs` for the Claude mapping. The common HTML and publisher are under `ui/template/` and supply both host projections.

## Local graph data and authorization

The [server composition](server/main.mjs) starts one [HTTP listener](backend/http/index.mjs) on `127.0.0.1` with an operating-system-assigned port. Loopback is the local network address of the same computer. The listener owns sockets, Host-header validation and shutdown. The [graph backend](backend/graph/index.mjs) and Claude's host bridge mount separate routes on that listener and own their respective authentication and origin policies. Built HTML and JavaScript are delivered by the application; the running data service uses the toolkit's Node.js process.

Model Context Protocol, or MCP, is the host channel for tools and application resources. Each MCP connection receives a random graph bearer credential, meaning possession of that token authorizes its defined graph-read scope. `show_graph` reads and validates the explicit root, then adds the requested path and its canonical filesystem path to that credential's selected roots. An explicitly requested rootless demonstration selects `null`. The graph route accepts only a root already selected for that credential. Graph credentials govern graph reads; Claude browser and Mod credentials govern host operations in their separate routes. A Mod is plugin code loaded into Claude's own session.

The shared HTML's inert JSON startup slot carries `graphBackend.url` and `graphBackend.token`. Codex obtains its selected root from the launch tool input or result; Claude's HTTP page carries its selected root in the startup slot. Server-Sent Events, or SSE, is an HTTP response that remains open and delivers successive data messages. Claude's HTTP page uses those values to open `/graph/events` directly through the [frontend stream client](application/graph/client/index.mjs). The Codex MCP App page reaches the backend through its MCP connection: the [relay client](application/graph/client/index.mjs) long-polls the page-only `watch_graph` tool, and the [graph relay](backend/relay/index.mjs) answers each request with the root's next change or an empty result at its time limit. A long poll is a request the server holds open until new data exists or a time limit passes. Both transports read one shared [live source](application/graph/live_source/index.mjs) per root; the [composition root](app/composition.mjs) pairs each page with its transport.

Codex Desktop `26.1007.9446.0` admits only `https:` and `wss:` origins into an MCP App page's CSP, so its sandboxed page cannot open the loopback HTTP route; [the decision record](../../docs/design/live-graph-transport-2026-10-14.md) records that finding and the relay transport. The graph route permits authenticated cross-origin reads for clients outside the page's own origin. Cross-origin resource sharing, or CORS, is the backend's browser-access policy; this route supplies the relevant request and preflight headers. Claude's host-action bridge uses an authenticated same-origin page, with the page and bridge sharing one origin. The MCP HTML resource declares the actual loopback origin in `_meta.ui.csp.connectDomains` on the returned resource contents. Content Security Policy, or CSP, controls the network requests the host's browser permits. The [MCP Apps CSP and CORS documentation](https://apps.extensions.modelcontextprotocol.io/api/documents/csp-and-cors.html) defines these separate controls, including localhost connections.

Codex's resource URI hashes the built HTML plus the backend startup data. A backend restart produces new credentials and a new resource identity, so a newly retrieved page receives the current connection. Resource identity, selected graph identity and host session identity each have their own owner.

## Save-to-render flow and lifecycle

1. [The graph service](application/graph/service/index.mjs) reads the selected root through `source/files.mjs` and prepares drawable data through `projection/graph.mjs`. `demo/` supplies the labeled rootless example.
2. [The live source](application/graph/live_source/index.mjs) owns one shared observation entry per subscribed root. It listens for filesystem changes relevant to `SKILL.md`, `graph.yaml`, `phases/` and `subgraphs/`, debounces save notifications for 75 milliseconds, and reconciles the source once per second. Reconciliation supplies coverage for missed events, phase-file edits outside the watcher filter and filesystems whose recursive watcher is unavailable. Each watcher notification and reconciliation tick first computes the root's fingerprint, a change detector built by [`skillFingerprint`](application/graph/source/files.mjs) from the path, size and modification time of every file under the root. The fingerprint reads file metadata only, skips dot entries, `node_modules` and `__pycache__`, and is bounded to 10,000 entries. The live source reads the graph only when the fingerprint differs from the last one it read.
3. Each read runs [`readGraphState`](application/graph/service/index.mjs). It applies the selection checks (an absolute path to a directory holding `SKILL.md` and `graph.yaml`), then compiles the root through the compile port, `compile(root) -> {status, diagnostics}`. The [runtime adapter](backend/runtime/index.mjs) implements that port: it spawns the runtime shell-free with `compile --no-cache <root>`, bounds the run to 30 seconds and 4 MiB of output, treats exit 0 as `passed` and exit 2 as `failed`, and rejects any other exit or a result outside the `gskill.compile-result.v1` contract. Its command is the JSON argument array in the `GRAPH_SKILL_RUNTIME` environment variable when set, otherwise the bundled Python named by the `release` in `~/.local/share/graph-skill/install.json`, run with `-I -B -X utf8 -m graph_skill_runtime`. The read yields one of three events:
   - `snapshot {data: {graph, skillRoot}}` when the runtime accepts the skill; the graph service projects root topology and phase kinds for drawing.
   - `invalid {skillRoot, diagnostics}` when the runtime rejects the skill; the event carries the runtime's compile diagnostics unchanged.
   - `error {message}` when a selection check fails, the runtime cannot be reached or answers outside its contract, or the canvas cannot draw a graph the runtime accepted; the message names that cause.

   The live source emits an event only when it differs from the root's last event, so a Markdown save that leaves the compile result and projection unchanged retains the existing snapshot. An existing page retains its backend startup data and its last valid graph across invalid and error events. On an invalid event the page shows the invalid-graph notice above that graph, and a later valid save produces a current snapshot through the same connection. [`show_graph`](server/main.mjs) opens the canvas for a snapshot or an invalid event; for an invalid event its structured content carries `graph: null` and `compile: {status, diagnostics}`, and its text lists each diagnostic's code, message and location. `inspect_graph` returns the same state, and `watch_graph` carries all three event kinds.
4. The graph backend writes those events to subscribed SSE responses, and the graph relay numbers them per root for `watch_graph` long polls. The page's graph client selects the root, receives each event over its transport and passes snapshots to the workbench. The workbench validates drawable data and preserves a selected node while that node still exists.

Saving a file completes this path through application-owned file observation, HTTP and rendering. The host adapter delivers launch selection and native operations. Its capability refresh updates host identity and operation availability; graph freshness comes from the independent graph stream. A page with valid graph startup data and a selected root can keep receiving graph data while host actions are unavailable.

The frontend client cancels its current request when the selected root changes or the page is disposed. It reconnects after a lost stream and ignores callbacks from superseded requests. Backend stream closure releases its subscription and heartbeat. The live source keeps a root for a 30-second retention window after its final subscriber leaves, then retires the root's watcher, timers and cached event. `show_graph` and `inspect_graph` read the root's current event through the live source's `current(root)`, so a page that subscribes within the window reuses that tool call's compile result. Graph credential closure ends its associated streams. Process cleanup closes all graph streams and watchers, settles Claude bridge receipts, removes exact owned temporary preview entries and closes the listener. Cleanup is triggered by standard-input closure or process signals in [the composition root](server/main.mjs).

## Host operations and presentation

The Host Port separates connection evidence, capability declarations and operation results. Startup data chooses a transport, while a connected identity and current capabilities determine the driver and whether each call may proceed. Codex uses `@modelcontextprotocol/ext-apps` `App` and `PostMessageTransport` for its host channel; Claude uses an authenticated same-origin HTTP bridge and a Mod running in the host. The [factory](adapters/factory/index.mjs) composes these paths, [detection](adapters/detection/index.mjs) interprets connection evidence, and [facade](adapters/facade/index.mjs) owns one host connection lifecycle, identity binding and guarded dispatch. The [Host catalog](ports/host/catalog.mjs) imports all 15 shared definitions, the [Codex driver registry](adapters/codex/driver/registry.mjs) maps every operation to its Codex module, and the [Claude Mod operations registry](adapters/claude/mod/operations/registry.mjs) maps every operation to its Claude module. [ADAPTER.md](ADAPTER.md) specifies each interface's request, host route and availability limit.

Canvas MCP tools retain their launch and inspection purposes. `show_graph` selects the root, returns graph diagnostics and provides the host-specific presentation result. `inspect_graph` performs an explicit read of a previously selected root. The server also registers an app-visible read-only `list_canvas_tools` tool that returns only `inspect_graph` and `list_canvas_tools` as page-callable references. Codex `tools.list` calls it through `App.callServerTool` and reports the originating-server scope; Claude `tools.list` reports its Mod's current session inventory. The frontend takes the selected root from host delivery and renders snapshots from its own backend connection. Explicit tool calls in the interface laboratory remain user-requested host operations.

Codex's presentation resource and session modules describe host widget delivery and reuse. Claude's presentation guidance and preview configuration support its native `preview_start`, navigation and tab-selection flow. That flow owns Graph display; Claude's generic `views.open` remains `unknown`. The Mod's `host_tools/`, `lifecycle/` and `operations/` read actual session/tool facts and execute declared host operations. The bridge owns their HTTP requests and receipts. The actual business `SKILL.md` remains user-owned and is reachable on request through the host's file tools and the laboratory's `files.openFile` sample.

## Installation and source selection

The installer remains separate from the page. `installer/download/`, `archive/`, `discovery/`, `hosts/`, `ownership/`, `locking/`, `runtime_layout/`, `runtime_payload/`, `install/`, `entry/`, `bundle/` and `verify_bundle/` keep their corresponding acquisition, host projection, state ownership and archive responsibilities. The source Mod under `adapters/claude/mod/` is mapped to the installed `claude-mod/` payload.

The [mode selector](installer/mode/__init__.py) changes which toolkit payload the existing installed user profiles reference. [Command dispatch](bin/graph-skill.mjs) builds a selected source for test mode and launches the mode entry with the installed private Python runtime; [host projections](installer/hosts/__init__.py) render the canvas server, follow-up hook, Skills and Claude Mod paths for either payload. [The installation planner](installer/install/__init__.py) verifies the immutable release and managed resources, and the selector records `source_mode`, the test root and hashes of built assets, the source command and both Skills' Markdown in the installation manifest. The CLI applies configuration and manifest changes under the installer lock. A repeated selection with matching hashes and owned resources returns `unchanged` without writing. The installed release still supplies private Node.js and Python and the command launchers. [Bundle assembly](installer/bundle/__init__.py) includes the mode entry and implementation for a later release. A source path, built payload, configured host profile and loaded host process are separate identities; selection and source tests do not establish a new host session's behavior.

## Rationale and acceptance scope

The shared local data path gives filesystem reads and observation one authoritative owner, and gives both frontend projections one connection contract. Host adapters can evolve their native capabilities while the same save-to-render path continues to use graph source, projection and stream semantics. [The earlier feasibility review](evidence/native-launch-20261012/architecture-feasibility.md) retains the rationale for the shared UI and neutral Host Port. The local application adds an independent data lifecycle to that separation.

[Backend integration tests](tests/backend/live.test.mjs) exercise real temporary files, atomic saves, phase type-file changes, invalid-input recovery, direct HTTP streaming and separation of graph credentials from host credentials. [The shared-HTML integration](tests/integration/shared-html.test.mjs) exercises the bundled server and a live selected-root update. [Protocol tests](tests/integration/protocol.test.mjs) bind the resource to backend startup data and verify the declared CSP. [Runtime adapter tests](tests/backend/runtime.test.mjs) exercise command derivation, compile-result parsing for passed, failed and out-of-contract output, and a spawned runtime that passes, fails, cannot start, crashes or times out; one opt-in case compiles the example skill with the installed runtime and is skipped when no installed runtime exists. [Live-source tests](tests/backend/live-source.test.mjs) exercise fingerprint gating, invalid-to-snapshot recovery, error events and the retention window. [Diagnostics tests](tests/graph/diagnostics.test.mjs) exercise the page's verbatim, bounded diagnostic input and the agent-facing diagnostic text. [The `watch_graph` integration](tests/integration/watch-graph.test.mjs) runs a real stdio `show_graph` on an invalid root, which opens the canvas with the runtime's diagnostics, and then receives the snapshot from a valid save over `watch_graph`. Apart from the opt-in case, these tests compile through test stand-ins that speak the compile-result contract: an [in-process compile port](tests/support/runtime.mjs) and [a fake runtime process](tests/support/fake-runtime.mjs). Native host observation of the invalid-graph notice and its recovery is pending on both hosts. A controlled browser observation of the valid-save path showed the recorded compiled candidate updating after a file save in an opaque iframe sandbox. This is a browser frame isolated from its containing page's origin. Its network policy allowed only the advertised local backend. That observation retains its recorded candidate identity and valid-save scope. The source tests and browser observation support their respective exercised paths. Loaded desktop access to loopback, actual installed server and Mod bytes, native host operations and retained document/canvas behavior require candidate-bound host observations. [VALIDATION.md](VALIDATION.md) owns measured run results and the remaining acceptance evidence. Earlier `0.3.4` host observations retain their exact historical candidate scope.
