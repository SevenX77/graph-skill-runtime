# Shared graph prototype

This document defines the implemented local prototype under goal `shared-graph-ui-feasibility`. Its [current baseline](VALIDATION.md#current-baseline-retained-skillmd-and-http-canvas-2026-10-10) owns source authority, decisions and evidence-bound acceptance. [MANUAL-TESTS.md](MANUAL-TESTS.md) defines native observations; the user may perform them, and agents may use Computer Use when needed but must release control immediately after use. Native effects require their own evidence. [ARCHITECTURE.md](ARCHITECTURE.md) owns source navigation. This source candidate is separate from the installed `0.3.3` payload and temporary native stages; publication requires the retained acceptance conditions.

## Interface and ownership

The prototype presents an actual Graph Skill graph in one common React `19.3.0` interface written in TypeScript `7.0.2`. React composes the page from reusable components; TypeScript checks data and operation shapes during development. The page displays the selected skill root, graph nodes and edges, the selected node and the exact root/graph/node context available for delivery. Mouse, Tab and Enter/Space select nodes. One built HTML interface serves Codex and Claude; host-specific embedded graph and connection data may vary. Each executable responsibility remains in its own directory under `src/graph_skill_toolkit/`, beside the independent Python runtime.

The shared page owns graph presentation, selection, controls and result display. The [host Port](ports/host/index.ts) is the typed operation contract used by the page. Each adapter implements that contract using its host's actual capabilities. Codex receives the page through an MCP App, which attaches an interactive page to a tool result. Claude receives the same page through the host's normal HTTP preview attachment; its Mod is a plugin whose event handlers run inside Claude Code. The canvas MCP process owns graph presentation data, the HTTP page/operation service and its temporary preview configuration. Both hosts receive the actual business `SKILL.md` identity through [presentation/index.mjs](presentation/index.mjs). The host opens that user-owned document through its file interface and retains it beside the canvas. The independent Python runtime remains responsible for graph execution and full portable-format validation.

The prototype provides nine explicit test controls: capability inspection and eight host actions. The page reads capability declarations when it connects; page loading and node selection do not send a prompt, open a file, invoke an inspection tool or execute a skill. Each control identifies its intended action and reports the adapter's capability and observed result. Actions require a real selected Skill root and a connected adapter. Unavailable actions remain disabled with an explanation. A user-triggered operation uses the displayed root and selected node as data, with identity and content validated at the adapter boundary.

## Test operations

| Control | Intended observable result | Acceptance boundary |
| --- | --- | --- |
| Inspect host capabilities | Display the capabilities reported by the connected adapter/host. | An adapter name alone does not establish any capability. |
| Open root / open file | Ask the host to reveal the displayed skill root in its file browser or open the root's identified document. | Record the actual view and exact path. Claude's measured folder reveal selects the root in its parent directory. Codex's agent-requested Windows Explorer action displays its contents; its embedded directory preview failed. |
| Draft prompt | Place or prepare a prompt for user review without requesting execution. | If the host has no draft interface, report it unavailable; sending the prompt is a different action. |
| Send and execute | Ask the host to accept an explicit prompt and begin its supported agent action. | Message acceptance, a started turn and completed work are separate observations. |
| Send context | Store the selected root/graph/node data for subsequent model use. | Claude appends same-root selection as labeled JSON to canvas-submitted text and retains its ordinary prompt hook. Verify the later response actually consumes that data. |
| List tools | Read the tools that the page is permitted to call and the current session actually exposes. | Claude filters the live inventory to the fixed canvas inspection tool. Codex has no list interface in the implemented protocol subset. |
| Inspect through MCP | Request the fixed read-only inspection tool for the displayed root. | Codex invokes its originating server directly. Claude submits one normal host turn and returns an accepted page receipt; the host conversation carries the real tool call and graph result. Acceptance requires that actual result. |
| Read and summarize the Skill | Ask the host to read the selected root's `SKILL.md` and `graph.yaml` and summarize its purpose and nodes, without executing or modifying the business Skill. | Completion requires observed reads of the exact files and the resulting summary. An accepted request receipt alone establishes neither actual loading/reading nor the completed summary. |

The controls test the operation contract; they are not a full graph editor. Business-file editing, arbitrary tools, new runtime execution features and global configuration changes are outside this prototype.

## Capability and result meaning

Each operation must retain enough information to identify the requested action, selected root/node when relevant, the adapter and the observed response. The interface uses the following meanings consistently; implementation field names may differ while preserving these distinctions.

| Meaning | Required evidence |
| --- | --- |
| Unavailable | The current adapter or connected host exposes no usable path for this operation under the measured conditions. This is not a universal host-support claim. |
| Rejected | The request reached the operation boundary and was explicitly refused or returned an error. Preserve the reason and distinguish invalid input from host rejection. |
| Request accepted | The documented channel acknowledged the request. State exactly what was acknowledged; do not infer the downstream effect. |
| Pending / outcome unknown | The request has no confirmed result, including a lost response after submission. Preserve its identity and inspect its receipt; do not automatically resend it. |
| Completed | The operation's specified effect was actually observed and linked to this request. For example, a tool result can complete a read call while a message acknowledgment cannot complete the work requested in that message. |
| Untested | The required observation has not been obtained. This is an evidence gap, not a negative capability result. |

The typed result statuses are `completed`, `accepted`, `pending`, `unsupported`, `rejected` and `error`; `unsupported` means unavailable in the connected adapter's current scope. Untested is an evidence judgment, not a protocol response. The page retains action results, supplied response data and request identifiers. A pending action initially disables further host actions to avoid duplicate effects. A Claude pending receipt can be queried with the separate result button using the same identifier; this is a read, not a resubmission. An uncertain Codex request requires observing the host because this transport has no receipt-query method. After checking the host, the user may select “已查看宿主，继续测试” (“I checked the host; continue testing”) to unblock other tests. That acknowledgment preserves the original unknown result and never resends its action.

The interface must not turn an error into apparent success or silently substitute a broader action. Codex's file control can explicitly report a rejected file extension and then request the same opening action through the host agent. A message acknowledgment remains acceptance of that request; the open view and the agent's finished work require their own observations.

## Host and delivery constraints

Codex uses a [compact MCP Apps transport](adapters/codex/transport/index.mjs) implementing the required `2026-01-26` protocol subset. MCP is the protocol carrying host tool calls and results. The transport negotiates initialization, binds messages to the parent window and its observed origin, correlates responses, preserves explicit errors and treats a response timeout or closed connection as an unknown effect. It supports the page's message, context, originating-server tool and advertised file-extension requests. When the host advertises `experimental["openai/message"].draft`, draft filling sends a message with `target="active"` and `send=false`; the measured host appends it while preserving the existing draft. An absent draft declaration produces an unavailable result. Host-wide tool listing remains unavailable; fixed tool calls target the originating server. The server uses the official MCP SDK, and the official `AppBridge` is the local interoperability test peer. Those checks establish their exercised protocol subset; native effects have the separate observations below.

The canvas server exposes `show_graph` and read-only `inspect_graph`. Both return `document.path`, the canonical business root's absolute `SKILL.md` path, and `document.fileUrl`, its encoded file URL. The explicitly requested demonstration has no business root or document. Inspection reads presentation data for an exact canonical root already selected through `show_graph` in the same connection, without compiling or executing business code or writing a preview. Both adapters request only that fixed inspection tool for the displayed root through their respective channels. These canvas tools are separate from the Python runtime's MCP tool set.

The normal Codex Skill opens or reuses the exact document through a standalone `open_in_codex` invocation with its absolute path and `line=1`. After that response, a separate invocation calls `show_graph` for the same root as the final presentation. The two calls occupy distinct tool batches, including when an orchestration tool can await them sequentially. The [focus decision](evidence/codex-native-20261011/focus-decision.md) owns the rationale and failed combined-call evidence. A queued file-open result remains pending until the view is observed. The host owns pane visibility and focus. Display hooks and Skill instructions coalesce the same operation/root into one request; file-preview, folder-opening, navigation and canvas controls are excluded from recursive display. Page loading performs no automatic file-opening or focus action.

Codex's [resource owner](adapters/codex/resource/index.mjs) supplies `availableDisplayModes=["fullscreen"]` and `preferredDisplayMode="fullscreen"` to both resource listing and reading. Here fullscreen names the host's canvas sidebar. The [session owner](adapters/codex/session/index.mjs) assigns one opaque `widgetSessionId` per canonical root within one server connection. Codex additionally scopes reuse by host conversation, server and resource identity. The host owns opening, hiding, reopening and disposal. The [closed-canvas decision](evidence/codex-native-20261011/closed-reopen-decision.md) explains why sole fullscreen availability preserves the sidebar mode when closing and supports later explicit redisplay. Current native observations establish reopening, repeated reuse and ordinary-edit activation in the measured Desktop version. Transport teardown removes its listener, closes the connection and settles outstanding requests as unknown outcomes; a subsequent action on a closed transport is rejected before sending.

Claude's page consumes the embedded graph snapshot and a browser connection descriptor. The MCP process starts one loopback HTTP service only on an explicit HTML `show_graph` request. It serves a neutral origin page and a random per-view graph path, and handles actions at the same origin. The graph document contains only its browser credential; the separate Mod credential stays in the host result. Browser and Mod bearer credentials travel in authorization headers rather than URLs or logs. The server rejects foreign origins and cross-site page reads; its page policy permits network connections only to the same origin. The browser adapter also rejects a mismatched page/bridge origin. The page submits a named action, and the Mod polls through `$.http.fetch` on `$.clock.every`. The bridge validates the selected root, permitted action and bounded input. Correlated receipts let an uncertain POST be followed by a manual GET without executing the action again.

HTML presentation requires two explicit identities: `skill_root` selects business files, and `preview_project_root` selects the live Claude project's `.claude/launch.json`. They may differ. The Mod obtains the latter from `$.session.root()` and overrides any model-supplied value. If the required session or preview APIs are unavailable, the graph result remains available with a display diagnostic; no static interactive fallback or guessed project root is used.

The [preview configuration owner](adapters/claude/preview_configuration/index.mjs) merges one uniquely named URL-only entry for the actual loopback origin. It preserves unrelated configuration, rejects redirected or hardlinked resources, checks ownership before replacement and serializes cooperating toolkit writers with a lock. File identity and revision checks detect intervening changes before replacement; they are not an operating-system guarantee against a noncooperating writer changing the file between the check and write. The host's supported attachment associates that running origin with the preview; the MCP process retains the HTTP server lifecycle.

Claude presentation requires `preview_start`, `navigate`, `tabs_context` and `tabs_select`. These native tools attach or open a view, navigate an HTTP tab, inspect tab identity and visibility, and select an existing tab. The Mod validates the exact selected business document independently from the live host project's launch configuration. Its ordered guidance inventories existing tabs, attaches HTTP and retains the actual returned tab ID, then inspects visibility and document presence. If the actual document is absent or the pane is hidden, the file opener opens or reuses `document.path`. The following inventory must identify one exact `document.fileUrl`, retain the HTTP tab and establish a displayed pane. An already-present document in a displayed pane is reused directly.

Navigation targets the retained HTTP tab, followed by selection of that same tab. After selection completes, a separate final context call must establish the active HTTP canvas, displayed pane, retained exact document and preserved pre-existing user pages. Both useful views remain open and repeated display must reuse their identities. [MANUAL-TESTS.md](MANUAL-TESTS.md) owns the observations. Ambiguous identity, duplicate views, a hidden pane, an unavailable tool or a refused step stops dependent presentation and leaves the actual result available for diagnosis. The host sequence uses observed IDs and returned URLs, preserves security settings and performs no tab closure. The document remains a file view; reverse-action tests use the interactive HTTP page.

The inspected Mod `ui.open` surface places a pane rendered from native components. The [bounded source decision](VALIDATION.md#three-page-counterevidence-and-replacement-decision) records the inspected interface and the evidence supporting Browser preview for the shared webpage.

The Mod uses `prompt.fill` in append mode and reports refusal while preserving the current draft. It uses `prompt.submit` for explicit send, root/file-opening requests, Skill reading and fixed graph inspection. Each accepted submission acknowledges the host request; the requested reply, view or query requires its own observation. Context synchronization stores root, graph and optional node identity without starting a turn. Canvas send appends saved selection only when it belongs to the same root, labeling the serialized JSON as user-supplied data. The ordinary prompt hook separately attaches that data to normal submissions. This explicit send path accounts for the host skipping the originating Mod's own prompt hook. The [context decision](evidence/reverse-resume-20261011/decision.json) and regression evidence retain the basis and earlier failure.

Tool listing intersects the live session inventory with the canvas's fixed inspection permission. For inspection, the Mod first checks that exact tool is present, then submits one normal host prompt naming `mcp__graph-skill-canvas__inspect_graph` and the selected root. A project projection substitutes its bound server name. The page receives `accepted`, while tool selection, normal permission checks and the actual graph response belong to the conversation. The [query-route decision](evidence/reverse-resume-20261011/query-route-decision.json) records the rejected direct-background attempt, including its consent-bearing variant, and the adopted conversation route. This route adds a model turn and latency. Its successful native result establishes the fixed inspection effect under the measured host conditions. The Mod retains preview guidance and leaves graph rendering with the shared page.

Session end cancels Mod polling, disconnects its views and clears its context and operation state. While the HTTP service remains reachable, an ended view reload returns an ended-session page and a loaded browser may inspect retained receipts. Normal MCP cleanup closes the HTTP listener and all sockets, including incomplete request bodies, and removes only unchanged owned preview configuration. If the process created the whole launch file and still owns its exact bytes, cleanup removes that file; otherwise it preserves unrelated entries and externally modified content. A stopped service makes old-page requests fail to fetch. The measured old page retained a stale ready header beside its action error; automatic tab retirement remains unverified. A subsequent explicit graph display creates the new connection and lazily restarts polling, including a host reset without a second session-start event. The business document remains intact. Delivered work whose response is lost retains an unknown outcome.

Claude HTML presentation checks the actual `SKILL.md` against the host file loader's **524,288-byte** limit before creating the view. Oversized documents receive an explicit error; the source remains intact. This bound applies to file preview. The HTTP graph service and pure snapshot renderer have no corresponding bound. [Isolated bundling evidence](evidence/prototype-bundle-size.json) measured minimal full SDK plus production React at **633,477 bytes**, and the compact transport at **4,735 bytes**; those historical measurements explain the retained compact transport. A larger SDK requires a separate scoped delivery review. The pure renderer varies only inert JSON within the common template. Native effects retain their candidate-specific evidence separately from build and simulated-host checks.
