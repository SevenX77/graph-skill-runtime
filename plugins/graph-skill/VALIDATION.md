### Adopted interface and ownership

The build retains one HTML template and one executable browser bundle, with exactly two browser adapters: Codex and Claude. The shared interface owns graph validation, drawing, root display, sizing and interactions. Claude receives a generated copy of that template with the current graph/root JSON embedded in a designated data slot. Codex retains MCP result delivery. Only the payload slot may differ between the documents; neither adapter may independently draw the graph. The former requirement that both delivered documents have identical whole-file bytes was an implementation method for proving a single interface. It is replaced by template and executable-code identity plus payload-only variation, because local preview needs a self-contained snapshot. The single-interface requirement is unchanged.

An explicit `show_graph` request for HTML presentation publishes `<canonical skill_root>/.gskill/canvas/<unique session-dir>/canvas.html`. The canvas MCP process owns a private directory for each selected root; its file path is stable for that root within the process and distinct from other processes and roots. The publisher must reject symlink or reparse-point parents, serialize updates, replace a file atomically only while its bytes match its last owned hash, and preserve externally changed files. A reparse point is a Windows filesystem entry that redirects path resolution, including a junction. Normal stdio shutdown triggers conditional cleanup of unchanged owned files and empty owned directories; modified or unknown entries remain preserved. Forced process termination can leave generated files for the owner to settle explicitly. MCP startup alone creates no files. Installation-resource ownership remains with the existing installer.

The generated document must fit the measured Claude preview reader's 524,288-byte limit (512 KiB). Oversize export returns a clear error without truncating the graph or document. The [decision](INSTALLATION-DECISIONS.md#local-html-preview-decision-2026-10-09) records the installed-client basis and its present verification boundary. This is a host-delivery limit, not an execution budget or observation deadline. Successful script execution is currently evidenced only for an HTML file within the selected Claude project; outside-project interactive rendering remains unverified.

The Claude Mod, a plugin observing host events, requests HTML presentation, executes the graph tool once, validates the returned local file path and preserves the graph result, core reference, text and existing context. It appends a reminder for a normal model-origin `mcp__Claude_Browser__preview_start` call whose `url` value is that local file path. The host's usual permission checks still apply. `tabs_context`, when available, supplies the separate displayed/hidden observation. Existing Skills and follow-up rules continue to trigger the graph call after an ordinary edit. Each successful graph call regenerates the snapshot; native preview then reloads that same file. This replaces the local HTTP service and browser polling. A preview without a later graph call remains a snapshot of its generation time, including after the server has closed.

Because HTML presentation writes an owned generated file, `show_graph` must declare `readOnlyHint=false`, `destructiveHint=false`, `idempotentHint=true` and `openWorldHint=false`. These tool annotations describe effects and repeatability to hosts. The file publisher is a server-side delivery utility, not a third browser adapter. The common root control continues to label Claude's actual action as copying the root; native folder opening remains unverified and must not be inferred from a working preview.
